# Agent 主循环与编排

Hermes 的 agent 核心：一条用户消息进来，怎么变成「模型调用 → 工具执行 → 再调用 → …」的闭环，
直到模型给出最终回答。整篇按一轮对话的真实执行顺序推进。

## Q1：Agent 主循环是干什么的？核心机制主要流程是什么？ ⭐⭐⭐

> **一句话：** 纯同步 while 循环，把一次 LLM 调用变成「调用—工具—观察—再调用」的闭环；退出条件是模型给出纯文本、预算到顶、中断或强制终止。

**主答：**

主循环解决的问题是把「一次 LLM 调用」这种开环请求，变成「调用—行动—观察—再调用」的闭环。没有它，模型只能说一段话；有了它，模型能连续使用工具、观察结果、修正行为，直到任务完成。

Hermes 的实现可以一句话概括：**一个纯同步的 while 循环**。不依赖 LangChain / LangGraph 这类编排框架，主循环本身没有事件循环、没有协程，就是一个线程里的循环体——需要异步的部分被圈在循环外面（比如 MCP 客户端，见 Q4）。每转一圈是一次迭代 (iteration)，一条用户消息从进门到出结果算一个轮次 (turn)。这个选择贯穿了全部设计——中断、预算、恢复都是围绕「单线程循环 + 明确的检查点」组织的。

先给全局图，一轮对话（一个 turn）的完整生命周期：

```mermaid
flowchart TD
    A[用户消息进入] --> B[轮次准入<br>等会话轮次租约]
    B --> C[轮次前置准备<br>恢复系统提示词 / 追加用户消息 /<br>发请求前的上下文压力检查]
    C --> D{循环条件：<br>迭代数与预算未耗尽？}
    D -- 迭代/预算耗尽 --> W[轮次收尾<br>完成判定 / 清理 / 持久化 /<br>记忆同步与钩子]
    D -- 是 --> E[迭代开始<br>处理改向 / 中断检查 /<br>计数与预算消费]
    E --> F[迭代准备<br>排空插话队列 / 注入预算提醒 /<br>消息修复与角色交替修复]
    F --> G[组装本次请求<br>历史副本化 + 工具参数规范化]
    G --> G2{压力闸门：<br>请求体积超限？}
    G2 -- 超限 --> H[上下文压缩<br>唯一的例外通道] --> D
    G2 -- 正常 --> I[发起模型调用<br>内层重试与错误恢复]
    I -- 调用不可恢复失败 --> W
    I -- 拿到响应 --> J{响应里<br>有工具调用？}
    J -- 有 --> K[工具轮：先持久化再执行<br>结果按序回填]
    K --> D
    J -- 没有，纯文本 --> W
    W --> L[返回最终回答]
```

顺着图讲：一条用户消息进来，先过**轮次准入**——同一个会话同时只允许一个轮次在跑，靠一把跨进程的会话轮次租约 (turn lease) 保证。准入后做**轮次前置准备**：从会话存储里逐字节恢复系统提示词（而不是重新构建）、把用户消息追加进历史、检查上下文压力决定要不要先压缩。然后进入主循环。循环的每一圈：处理用户改向、做中断检查、消费预算，然后准备消息、把历史组装成本次请求、过上下文压力闸门、发起模型调用（带内层的重试与降级）。拿到响应后看内容：有工具调用就执行工具、把结果贴回历史，进入下一圈；是纯文本就跳出循环，做**轮次收尾**——完成判定、清理、持久化、记忆同步——把最终回答交还给调用方。

两个贯穿全局的约束先立住，后面每个环节都会撞见：一是**迭代有硬上限**（次数封顶）**加一份可退款的迭代预算 (iteration budget)**，每个 agent 一份、父子独立，退款规则见 Q3；二是**每会话的提示词缓存 (prompt cache) 不可破坏**——系统提示词在一个会话内必须字节稳定，历史消息一旦持久化就不再改写，循环运行中任何想注入内容的动作只能走用户消息或工具结果的通道，唯一被允许改写历史的操作是上下文压缩。

### 追问：turn 和 iteration 是什么关系？

区别在计数口径：迭代按模型调用数计，工具执行不额外计。某些特殊轮次（如纯程序化代码执行的轮次）会把刚消费的预算退回，但只退预算、调用计数照常增加；改向和降级的重启才是计数与预算一起退。

### 追问：和 LangChain / LangGraph 的 executor 比，本质区别是什么？

三点。第一，控制权在自己手里：循环、重试、降级、中断全是自己的代码，出问题改自己的，不用穿透框架抽象；代价是所有脏活——错误分类、上下文压缩、消息格式修复——都得自己写，这个库光循环阶段文件就有三十多个。第二，它是同步的：框架的 agent executor 大多建立在异步运行时上，hermes 选择单线程循环，状态的推理成本远低于跨协程的状态同步（为什么敢这么做，Q4 展开）。第三，核心只有一份、处处复用：同一份循环代码跑在 CLI、约二十个消息平台、定时任务、子代理上，所有平台差异都被挡在循环之外（回调、平台适配层），循环不感知自己跑在哪。

### 追问：业界还有 plan-and-execute 那种先规划再执行的路线，hermes 为什么不这么做？

显式规划（先让模型出完整计划、再逐步执行）不在循环里做。hermes 把规划能力下放到工具层：待办、看板这类计划载体本身就是工具，由模型自己维护，「下一步干什么」仍是模型每轮的决定。收益是循环极简、随时可以改向——用户中途插话不需要重排一份计划；代价是没有全局计划护航，模型可能绕路甚至原地打转，兜底是迭代硬顶和护栏（同一调用反复触发的检测）。这是一次「把智能放在模型侧还是放在执行器侧」的取舍，hermes 一贯选前者。

## Q2：一条用户消息进来，到模型第一次被调用之间，都发生了什么？ ⭐

**主答：**

三步：准入、恢复、检查。

**准入**：先拿那个会话的轮次租约——同一个会话同时只允许一个轮次在跑，跨进程有效。后来者排队等待：最长半小时、可被用户中断；软中断时未消费的消息随结果带回供下次投递，等到超时则提示重发。不存在两个轮次并发改写同一段历史。

**恢复**：系统提示词**从会话存储里逐字节恢复**，而不是按当前配置重建——提示词缓存按前缀字节匹配，重建一遍哪怕语义相同、字节不同就全量失效。配套的工具列表冻结同理：数组前缀和顺序按会话首次发送的形态恢复，只有切换运行界面才允许尾部追加。只有运行时身份变了（换了模型、换了工作目录）才允许重建提示词，重建记账一次缓存破坏。

**检查**：发请求前做一次上下文压力评估，超限先压缩再发请求。压力估算三层按优先级取用：provider 上次报的真实用量锚点 > 剪枝后的线上载荷估算 > 通用粗估；且粗估不许低于上次真实值——非英文文本按字符粗估会低估近一倍，低估放行一个超限请求，在会静默截断的 provider 上就是无限截断循环。

### 追问：为什么需要轮次租约？谁会跟谁并发？

并发来自四面八方：网关投递撞上还在跑的轮次、定时任务投递和用户消息撞车、后台审查和前台轮次共用会话身份。没有租约，两个轮次并发改同一段历史，持久化顺序、缓存前缀、消息交替全部崩坏。租约把「会话」变成串行化的资源，持有者崩溃后租约会超时释放，不会把会话锁死。

## Q3：主循环的一圈迭代由哪些阶段组成？ ⭐⭐

**主答：**

循环条件一句话：迭代数没超上限、预算还有余额，就再来一圈（另外还留了一条很窄的宽限通道，见下面追问）。循环怎么停也一口气说全——四类退出：模型给出纯文本（正常完成）、迭代或预算耗尽（到顶）、中断（用户叫停）、强制终止（护栏触发、落库失败这类，轮次直接判负）。

每一圈的骨架是固定的阶段序列：

1. **迭代开始**——先应用用户上一圈发来的改向（见 Q4），然后做中断检查，再计数加一、消费一次预算（消费失败即判预算耗尽，退出循环）；
2. **迭代准备**——触发平台步骤回调、排空发请求前最后到达的用户插话、注入预算提醒、修复历史里的消息问题（角色交替修复、工具参数消毒）；
3. **组装请求**——把持久化历史克隆成一次性请求副本，工具调用参数做规范化；
4. **压力闸门**——请求组装完后按真实体积再查一次上下文压力，超了就压缩后回炉重走；
5. **模型调用**——带着内层重试循环发起调用（Q7 展开）；
6. **响应分支**——有工具调用走工具轮（Q6），纯文本走收尾（Q8）。

这套骨架在代码里被拆成三十多个阶段文件，阶段之间靠一套隐式约定流转状态（每个阶段拿走自己要的状态、返回一个「继续 / 重跑 / 跳出 / 直接返回」的判定和改过的字段），不靠显式接口。这样加一个阶段的成本约等于写一个函数，每个阶段也能独立测试；代价是控制流变成隐式的——读懂一圈迭代的真实路径，得先懂这套约定。用可维护性换可读性，作者认为值。

### 追问：迭代上限和迭代预算是什么关系？默认值是多少？

上限是硬顶，碰线即停；预算是一份可退款的额度，覆盖「这次迭代不该算数」的情况。默认值分层：agent 类本身的构造默认是**不设限**；500 是命令行应用层的默认值，可通过配置改。子代理另有一套更小的独立上限，官方文档写 50，源码里实际默认值已是 250——官方文档还没跟上源码。

### 追问：预算在什么情况下退款？

原则一句话：**没到 provider、或不算一次真实模型轮次的迭代，都退**。典型场景：用户改向导致请求被取消、发请求前压缩（这一圈根本没发出去）、降级到备用 provider 后的重启、整轮只做程序化代码执行的调用（这类调用廉价如 RPC，不该烧预算，且只退预算不退调用计数）。退款显然有被滥用的风险——一个不断触发重启的轮次可以无限退款、无限占着会话租约。所以改向重启和降级重启共用一个按轮次累计的重启上限，超限强制结束轮次；压缩重启则受重试次数约束，压缩了但没压够空间也不能无限循环。预算耗尽前还可以配置一次性提醒，注入到最近一条工具结果尾部，催模型先把进展写下来，但提醒不延长硬预算。

### 追问：循环条件里那条很窄的宽限通道是什么？

置位条件很窄：推理模型走 Responses 通道连续三次「只思考不产出」、被迫降级到备用 provider、而预算恰好耗尽——就给备用 provider 额外放行一圈（普通迭代，工具照常可调），否则循环会在备用 provider 得到说话机会之前就退出。真正「预算耗尽后让模型把话说完」的机制在收尾阶段（Q8）。

## Q4：为什么选纯同步？异步的代价是什么？ ⭐⭐⭐

> **一句话：** 单线程循环换来状态的可推理性；中断靠「请求在后台线程、主线程等三个事件」，工具并发靠受控线程池——同步的语义，不牺牲响应。

**主答：**

理由是**可推理性**。agent 的状态（历史、预算、压缩进度）全在一个线程里流转，检查点就是循环体的每一行边界——中断在每圈开头查，预算在消费点扣，恢复逻辑不需要考虑「恢复到哪个协程的哪个 await」。异步带来的吞吐收益对一个「每圈等一次几秒到几十秒的模型调用」的负载毫无意义，而它引入的跨协程状态同步、取消传播、异常逃逸的复杂度，恰恰是 agent 这种重状态程序最付不起的。

同步不等于迟钝，三件事单独说：

**响应用户动作**。每次模型调用跑在一个后台工作线程里，主线程在三个信号上等待：响应就绪、中断事件、超时。中断到来时主线程立刻从等待里返回，那个 HTTP 请求被放弃——每个请求持有一个独立的客户端连接，中断只关掉自己这一个；还有一个「僵死调用检测器」负责杀掉挂死的连接并抛错，让重试循环接手。被放弃的是这次未完成的响应本身；已经流出的可见文本会留下记录，作为一条助手消息进历史——下一轮对话模型能看到「自己被打断前说到哪了」。

**流式输出**。模型调用在工作线程里跑，流式片段经回调直接送给界面，主线程只负责等三种结局，循环本身不参与渲染。没有界面的场景（定时任务、子代理）也默认开流式——流式分片兼作连接健康信号，比等整体响应更早发现僵死连接。也因此，中断一个流式请求时，已经展示给用户的文本必须在收尾时被捞回来当正式回答（Q8 讲这个保证）。

**工具并发**。工具的并行执行靠受控的线程池（Q6），不需要整个循环异步化。

### 追问：用户在轮次进行中的「停止」「插话」「改向」是三件不同的事吗？

是三件事，容易混：

- **停止**是终止轮次。中断生效后，已流出的文本保留为记录，轮次以中断态收尾。
- **插话 (steer)** 不打断任何东西：文本先排队，等这一批工具结果落地后，作为一条独立的用户消息插到最后一条工具结果后面；当前还没有工具结果就继续排队等下个时机。模型下一圈自然看到它。
- **改向 (redirect)** 才是「响应期间插话的强化版」：取消在途的那一次请求，把修正作为真实的用户消息追加（需要时补一条助手占位行维持消息交替），循环从修正点重建请求继续跑，被取消的那次调用退回预算。工具正在执行时改向会退化成插话——绝不杀正在跑的工具。

为什么插话和改向都要「新插一行」而不是涂改已有消息？因为历史是追加式持久化的，已经写库的行改一个字节，磁盘上的重放内容和线上请求就发散了，而且更早的消息大概率已在 provider 侧命中缓存，改写等于主动放弃缓存。这是全系统一条铁律：**注入永远是新增行，不改写已落库的行**——恢复类合成提示（空响应重问、截断续写）也都遵循它；插话/改向的特殊处仅在于它们是仅有的两类**由用户发起**的合成行。

### 追问：模型响应和用户改向同时到达怎么办？

竞态规则：改向优先。响应作废、从修正重建——两个同时到达，判定归用户。反过来，如果改向和错误处理撞上（比如改向取消了请求、请求以中断错误浮出），错误处理器会先分辨「这是用户在转向还是真出事」：改向引起的取消保留修正内容走重建，只有真正的停止才走中断收尾。

### 追问：MCP 这类异步协议栈，怎么接进同步循环？

边界隔离。MCP 客户端是异步协议栈，但它被圈在工具子系统里：一个专职后台线程跑自己的事件循环，同步侧把调用安全地递过去、带着超时等结果——对主循环来说，一个 MCP 工具调用和一次本地函数调用没有区别，都是阻塞调用。这也体现了一条贯穿 hermes 的设计原则：主循环核心保持极简，复杂的东西全部推到外围，外围要用什么形态的运行时自己解决，核心不掺和。

## Q5：模型返回之后，循环怎么决定「继续干活」还是「结束回答」？ ⭐⭐

**主答：**

分支只看一件事：响应里有没有工具调用。有，就走工具轮，把结果贴回历史，回循环顶上继续；没有，就是模型认为任务完成，文本作为最终回答，走收尾。这就是 ReAct 的「行动—观察」循环在工程上的全部骨架——循环本身极简，复杂度全在分支两侧的异常处理里。

具体说，拿到响应先做**归一化**：把不同 provider 的返回差异抹平成统一内部格式（hermes 内部用一套消息格式做通用表示，各家协议在出入两端转换）。归一化过程中要识别一批「病态响应」：

- **工具调用后空响应**——模型调了工具、拿到结果，却回了个空文本。合成一条提示贴回去：「工具结果在上面，请处理并继续」，而不是把空字符串当最终回答交给用户；
- **截断**——输出顶到长度上限被切断。分两种：纯文本截断不重发原请求（会原样再截一次），而是合成续写提示，同时逐次调高输出上限；工具调用的参数被截断则反过来——带着抬高后的上限重发同一个调用（次数有限），仍不完整就拒绝执行、直接收尾，绝不带着残缺参数硬干。极端场景下还会对下一次调用临时关闭思考模式——思考内容也算输出预算，「想太久把答案挤没了」的场景下继续开着思考只会再次截断；
- **只思考不说话**——推理模型走 Responses 通道（模型与平台之间的一种 API 通道，与通用通道相对）时，可能返回纯内部推理、没有任何可见内容。原样重试只会得到一模一样的结果，所以定向提示它「别想了，直接说答案或发工具调用」。通用通道上的同类问题没有这条捷径，走的是另一条阶梯：先把推理内容回放为临时上下文试着续写（有次数上限），仍空则按空响应重试、降级、终局。

这些处理共同的形状是：**不放弃这轮，往对话里注入一条定向的合成提示，把模型拉回正轨**。合成提示走消息通道、写入时带身份标记，从不碰系统提示词——又是那条缓存约束。

### 追问：模型说完成了就算完成吗？这么设计没有代价？

默认交给模型，但留了可选的收口闸门。模型给出纯文本答案时，几类条件性开启的闸门（比如「代码编辑后未经核实就想收尾」的检查、特定运行模式的收尾守卫）可以把这个答案拦下：答案被扣住，注入一条合成用户消息催模型先自查再答，循环继续；被扣住的候选答案会保留着，作为预算耗尽时的兜底回答。默认不开——不越权代替模型判断完成，运行方按场景决定要不要加这道收口。代价在另一头同样存在：模型可能过早收笔（靠闸门和追问兜）或赖着不收笔（靠迭代硬顶和护栏兜）——把完成裁判权交给模型，工程上换来的是退出条件极简可靠。

## Q6：工具调用在这个循环里是怎么执行、怎么回到循环的？ ⭐⭐⭐

> **一句话：** 先落库后执行（崩溃恢复的安全底线）；多调用按「并行安全段 + 顺序屏障」保守分段；工具失败归一化为观察结果回填，只有落库失败和护栏才终止轮次。

**主答：**

拿到带工具调用的响应后，工具轮按固定顺序做七件事：**校验、裁剪、落库、批次编排执行、循环侧拦截、护栏、压缩与心跳**。

**校验**：模型发的调用先过名字和参数校验。一批调用里混了不存在的工具名时，处理很克制——助手消息保留全部发射（每个调用都要有对应结果，这是消息协议的硬要求），但非法的那个直接得到一条错误结果、不执行，合法的照常跑。参数字符串坏了就地修复；修不了的注入一条错误工具结果让模型重发，绝不静默丢弃。

**裁剪**：去重、给子代理委派类调用设数量上限——模型在一条响应里塞十几个委派任务是真实发生过的事。

**落库**：这是全流程最重要的不变量——**先持久化、后执行**。工具调用轮的消息（助手要调什么工具）必须在任何副作用发生前进会话库。理由是崩溃恢复：如果执行了一个删文件的工具、进程随后被杀，重启恢复会话时必须能看到「我正要/已经调了这个工具」，否则用户重发消息、模型再删一次文件。反过来，如果持久化本身失败，宁可整轮失败，也不从纯内存状态执行工具。

**批次编排**：单个调用直接执行；多个调用先做**分段规划**——把批次切成「并行安全段」和顺序屏障，按段执行（安全段内并发、屏障处串行），判定规则很保守（细节见下面追问），结果永远按模型发射的顺序回填历史，不管实际完成先后。

**循环侧拦截**：一类「agent 级工具」完全不走工具注册表 (tool registry)——待办管理、记忆写入、会话内检索、子代理委派这些需要读改 agent 自身状态的工具，在循环侧直接拦截执行（注册表里的通用工具拿不到 agent 内部状态）。危险操作的人工审批也在这一步：审批请求阻塞等待用户决定，结果同样以工具结果的形式回填给模型（审批机制细节在安全篇展开）。

**护栏**：执行后检查有没有触发「护栏停止」——典型的是模型反复发起完全相同的调用（卡死循环）。触发时本轮直接结束：把带原因的护栏说明附在最后一条工具结果上（留给历史），另合成一段面向用户的收尾回答（为什么停、怎么继续），不再回循环。

**压缩与心跳**：工具结果可能很大，贴回历史后做一次工具后压缩评估，超阈值就地压缩。然后上报一次活跃心跳——工具执行这段不产生活跃信号，紧接着的模型调用又慢，中间这段监测空窗可能被网关判成会话不活跃而误杀会话，所以主动摸一下再继续。

### 追问：一批里多个工具调用，谁并行、谁串行，怎么定？

保守的白名单制，宁可不并行也不赌正确性：一组已知只读、无共享可变状态的工具在白名单里，可并行；文件类工具按路径重叠准入——读可以共享同一棵子树，写和任何重叠的读写冲突；向用户提问这类交互工具永远充当屏障；不在任何安全域里的默认串行。就算判定错了，代价也只是少并行一点——因为规则本身存疑就串行，永远不会让两个可疑的调用并发。结果按发射顺序回填还有一个理由——顺序稳定才能保证重放和缓存前缀稳定，先完成先回填会每轮打乱历史。

### 追问：工具自己挂了（抛异常、超时）怎么办？整轮失败吗？

不。工具执行层的异常、超时、被取消都被归一化成结构化的**错误结果**——对循环来说它就是一条普通的工具结果，回填给模型，模型看到失败原因自己换办法（改参数、换工具、或告诉用户做不成）。错误文本有长度上限，防止巨型异常栈把历史撑爆。只有两类情况会结束整轮：落库失败（不能从内存态继续）和护栏触发（继续只会循环）。把「工具失败」归为观察而非事故，是 agent 和普通 RPC 编排的分水岭。

### 追问：先持久化再执行，性能代价不大吗？

一次本地 SQLite 追加，相对动辄数秒的工具执行和模型调用，可以忽略。这个顺序换来的恢复语义是「执行过的必留痕」，对带破坏性工具的 agent 这是安全底线，不是优化点。

## Q7：模型调用出错怎么办？重试和降级是怎么组织的？ ⭐⭐⭐

> **一句话：** 先分类再行动——错误分类器给出「重试 / 压缩 / 换凭证 / 换 provider」四类处置，逐级升级；降级必回炉重走前置检查；计费和内容政策类不重试直接终局。

**主答：**

（回到 Q3 骨架里「模型调用」那一站，补它的异常支线。）

错误处理是两层嵌套的防线：**内层**包着单次模型调用（同一迭代内重试），**外层**是主循环自己的异常防线。

内层的核心是**先分类、再行动**。每个异常先进分类器，输出一个结构化判定：可否重试、是否该压缩上下文、是否该轮换凭证、是否该切换备用 provider。四类处置不互斥，按逐级升级的顺序试：凭证类错误（认证失败）先试刷新凭证、轮换凭证池；provider 级故障（限流、服务端错误）按配置的备用链逐个降级；上下文超限错误回炉压缩；全部无效才把错误结算成轮次失败。几个容易踩的细节：

- **降级必须回炉**。切到备用 provider 不是原地重发——备用模型的上下文窗口可能更小，所以每次降级激活都以「重建消息、重新过压力闸门」收场，让前置检查对着新窗口重新评估。降级还退回本次迭代的预算，因为失败不是模型的错（退款的上限规则 Q3 已说：改向重启与降级重启共用按轮次累计的上限）。
- **限流有跨会话记忆——对内置了这套机制的 provider**（以 hermes 自家的服务为例）：限流窗口写在共享文件里，别的会话撞了限流，本会话发起前就会得知并直接走降级，而不是把注定失败的请求发出去再等 429。其他 provider 的限流走凭证池轮换和降级链，各会话独立。
- **外层防线**：漏出内层的异常每轮对话有次数上限（个位数），超过就结算失败。
- **不可重试白名单**：计费耗尽、内容政策拦截这类错误，重试注定得到同样结果，直接带着结构化的失败原因终止轮次——失败原因里带「是否值得重试」的标记，让上层界面只在重跑有意义时才显示重试按钮。

### 追问：重试的节奏呢？几次、等多久、会不会越退避越糟？

次数上，单次模型调用默认最多重试三次（可配），每次新的模型调用重新计数；外面再套每轮八次的外层异常上限。间隔上是带随机抖动的指数阶梯：基准间隔起步、逐次翻倍、有上限，抖动是特意加的——大量会话同时撞同一个限流 provider 时，整齐的固定间隔会叠成重试风暴，抖动把它们错开。provider 在响应头里给了明确的等待指示（限流重试时长）时优先遵从。等待本身是可中断的：用户按停止不必等到退避结束，立刻生效。

### 追问：重试会不会把对话历史改乱？

不会，这是刻意的架构隔离：持久化历史和线上请求是两个副本，每次请求从历史做结构克隆，所有请求期的改写（参数规范化、缓存标记）只发生在克隆上；历史侧的任何修复（角色交替修复、参数消毒）有自己的独立通道并同步回库。请求侧怎么折腾，存储里的会话不动如山。

## Q8：一个轮次是怎么收尾的？怎么判断「完成」？ ⭐

**主答：**

循环退出后，多数路径（正常完成、到顶、中断这类跳出循环的退出）进入一条固定的收尾管线；少数终局失败（内容政策拦截、重试彻底耗尽这类自带结论的）不走管线、直接带结果返回，只补一道失败边界处理（见本问末尾）。管线步骤：

1. **预算耗尽的兜底判定**——轮次干净走到预算耗尽（没失败、没中断）而没有最终回答时，校验闸门扣住的候选答案此刻转正（不再多花一次调用）；没有候选答案才补发总结请求；
2. **静默停止修复**——轮次非中断地掉出循环、尾部停在工具结果上没有任何助手文本（用户侧表现为界面转圈后无声无息）时，标记失败并合成一句可见解释，把尾部修成合法的消息交替；
3. **完成判定**——「完成」不等于「有回答」：回答存在、不失败、不中断、迭代没超限，四条同时成立（纯文本自然收尾是超限的例外）；判定先于清理和落库算出；
4. **清理**——延迟到此刻的标题升级、轨迹保存、资源回收，全部尽力而为、失败不阻塞；
5. **持久化**——固定顺序：清掉尾部残留的重试脚手架（用户发出的插话/改向是真实用户行，不清）→ 捞回已流出的文本当最终回答（**用户已经看到的话，不许消失**）→ 输出变换 → 补写历史尾部 → 可选的增量压缩（默认关闭；开启后每轮把最老一段未压缩交互折进滚动摘要，代价是重写已落库历史、每轮破坏一次缓存）→ 落库；
6. **记忆与钩子**——同步外部记忆服务、触发后台记忆/技能复盘（回答交付之后异步跑）、通知上下文引擎和生命周期钩子。

失败轮还有一道边界处理：若持久尾部留在用户消息上（模型一句话没说），补一条标记过的助手边界行——否则下一条用户消息接在用户消息后面，违反交替约定，部分 provider 直接拒收整个请求；上下文超限类失败除外（往超限会话再追加只会更糟，靠轮换新会话解决）。

### 追问：预算耗尽后，模型的话就说一半断掉吗？

不会。先看有没有兜底：校验闸门扣住的候选答案这时转正（见第 1 步），不花新调用。没有兜底才补发一次「总结请求」：拿现有历史再调一次模型，只要求它把已完成的进展总结成最终回答。有意思的是这次请求在通用通道上**仍然带着工具清单**——不是疏忽，是缓存：工具清单是请求前缀的一部分，摘掉它前缀就变了，这次调用会从缓存里一个字节都借不到；带上工具、但模型真发了工具调用也不执行（直接丢弃），省钱和防失控两头都占。这是「缓存不变量反过来约束设计」的典型案例。

## Q9：这套设计最大的代价是什么？让你改，你会改哪里？ ⭐

**主答：**

三个代价，按痛的程度排：

**一是中断的线程模型**。「调用在后台线程、主线程三事件等待」意味着中断的实现是放弃线程而非取消计算——被放弃的 HTTP 连接靠独立客户端和僵死检测器收拾。这在单会话串行的前提下够用，但如果要一个进程跑大量并发会话，一个会话一个线程的模型在内存和调度上都先撞墙。真到那个规模，我会把「单会话串行」保住（这个不变量是对的），把执行引擎换成少量事件循环线程池——也就是同步的语义、异步的执行。这是整个设计里最值得动的一刀，也是最伤筋动骨的一刀。

**二是阶段化状态传递的理解成本**。循环状态按隐式约定在三十多个文件间流转，控制流被摊进各阶段的判定语义里。新人的第一个问题永远是「这个字段在哪被改的」。缓解办法是有的——更严格的阶段间数据流文档、或者把判定收敛成更少的几种类型——但我不确定值得：这个系统的高复杂度是问题域固有的（一个要在二十个平台上扛住各种 provider 怪癖的循环），拆散至少让每块能独立测试和演进。真要改，我会先改测试表达力而不是结构。

**三是缓存不变量带来的滞后性**。会话中途不能改系统提示词、不能换工具集：在 CLI 这类界面里，「用户中途装了个新工具」只能等下个会话生效；常驻界面有折中——工具配置的变化会让下一轮重建提示词、立即生效，代价是记账一次缓存破坏。用户感知是「为什么不灵/为什么变慢了」。这是省钱的代价（缓存命中率就是钱），我认为整体划算，但值得给用户一个显式的「重启会话以生效」提示，而不是静默延迟。

这三个代价同源：hermes 把「个人 agent 的长对话成本」放在了「系统吞吐」和「代码直观」前面。评价一个 agent 架构，先看它付出了什么代价、为什么付，再看付得值不值。
